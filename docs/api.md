# API reference

Everything is JSON over HTTP. There is no versioning and no public API — this is
the interface the PISCOC dashboard itself uses, documented so other clients and
scripts can use it too.

The endpoint tables near the bottom are generated by walking the running server's
router, so they cannot drift from reality. Regenerate them with:

```bash
npx tsx scripts/generate-api-docs.mjs          # rewrite the tables
npx tsx scripts/generate-api-docs.mjs --check  # fail if they are stale
```

## Access levels

| Level | How a request proves itself |
|---|---|
| **public** | Nothing required. |
| **auth** | Session cookie from `POST /api/login`. |
| **admin** | The same, for a user with the admin flag. |
| **token** | A contributor upload link. The secret in the URL is the whole credential; no session is involved. |
| **webhook** | Shared secret in the `x-webhook-secret` header, set via `WEBHOOK_SECRET`. |

Signing in is `POST /api/login` with `{username, password}`. Failed attempts are
limited to 10 per 15 minutes per IP. User objects never include the password
hash.

Admin covers account management, writing integration credentials and the
public-link toggle. It does **not** cover Airtable syncs, pushes or status reads
— any signed-in user can run those.

## CSRF

Session cookies are issued `SameSite=None` in production so the CMS can be
embedded cross-origin, which means browsers attach them to cross-site requests.
**Every state-changing request therefore needs a CSRF token.**

The server sets a readable `csrf_token` cookie. Echo it in the `x-csrf-token`
header on every `POST`, `PUT`, `PATCH` and `DELETE`:

```js
fetch('/api/articles/1', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json', 'x-csrf-token': csrfToken },
  credentials: 'include',
  body: JSON.stringify({ title: 'New title' }),
});
```

In the dashboard, `apiRequest()` and `apiUpload()` in
`client/src/lib/queryClient.ts` do this for you. Without the header you get
`403 Missing CSRF token`; with a mismatched one, `403 Invalid CSRF token`.

Three things are exempt, because their callers have no cookie to send:

- the exact path `POST /api/public/team-member-update` — public, gated instead by
  the team-upload setting and a rate limit;
- everything under `/api/public-upload/` — authorized by the token in the URL;
- everything under `/api/webhooks/` — authorized by the shared secret.

The match is **exact for the first and by prefix for the other two**. That
distinction is load-bearing: `/api/public/` is not prefix-exempt, because it also
hosts the admin-only `POST /api/public/team-upload-status`, which must stay
protected.

## Errors

Every error is JSON:

```json
{ "message": "Article not found" }
```

Validation failures add the offending fields:

```json
{
  "message": "Validation error",
  "errors": [{ "path": "title", "message": "Required" }]
}
```

Some errors carry structured context under `details` instead.

| Status | Meaning |
|---|---|
| 400 | Malformed input, failed validation, unusable upload |
| 401 | Not signed in, or an invalid/expired upload link |
| 403 | Signed in but not permitted; missing or bad CSRF token |
| 404 | No such record, or no such endpoint |
| 409 | Conflicts with current state (duplicate username, session already open) |
| 413 | File exceeds the configured limit |
| 429 | Rate limited |
| 500 | Server fault. Details are logged, never returned. |

An unknown path under `/api` returns `404 {"message":"Unknown API endpoint"}`
rather than the dashboard's HTML.

## Rate limits

In-memory and per process, so they are per-instance rather than global.

| Surface | Limit |
|---|---|
| `POST /api/login` | 10 failed attempts / 15 min |
| Contributor and public uploads | 40 / 15 min |
| Upload-link metadata reads | 120 / 15 min |
| Public reads | 300 / 15 min |

All are keyed by IP, including the contributor upload routes — contributors
behind one NAT share a budget.

## Publishing an article

`PUT /api/articles/:id` is the main write path. When the change publishes or
unpublishes the article, the server also pushes it to Airtable and notifies the
live site to drop its cached copy. Both are best-effort: the row is already
saved, so a failure there is logged rather than returned as an error.

Pass `forceWebhook: true` in the body to trigger those effects for an edit that
would not otherwise qualify.

Ordinary draft-to-draft edits deliberately do neither.

## Contributor uploads

An editor mints a link, a contributor uses it, nobody needs an account.

The link is a random 256-bit secret, stored only as a SHA-256 hash and returned
in plaintext exactly once, at creation. It is scoped to one article and an
explicit set of asset types, and lasts 14 days by default
(`UPLOAD_TOKEN_TTL_DAYS`, or `ttlDays` per link).

```
POST   /api/upload-links                        (auth)   -> 201 { token, url, expiresAt, uploadTypes }
GET    /api/upload-links/:articleId             (auth)   -> metadata only, never the secret
DELETE /api/upload-links/:id                    (auth)   revoke

GET    /api/public-upload/:token                (token)  what this link allows
POST   /api/public-upload/:token/image          (token)  multipart, field "file"
POST   /api/public-upload/:token/instagram-image(token)  multipart, field "file"
POST   /api/public-upload/:token/html-zip       (token)  multipart, field "file"
POST   /api/public-upload/:token/complete       (token)  finish a re-upload session
```

`GET /api/public-upload/:token` answers with what the contributor needs to render
their page:

```json
{
  "article": { "id": 1, "title": "…", "hasContent": true,
               "hasCoverImage": false, "hasInstagramImage": false },
  "uploadTypes": ["image", "instagram-image", "html-zip"],
  "expiresAt": "2026-09-06T00:00:00.000Z",
  "isReuploadSession": true
}
```

A rejected link is specific about why: not valid, revoked, expired, already used
(all 401), or does not accept that file type (403). Validation runs before the
file is read, so a bad link never causes a byte to be written to disk.

**The multipart field name is `file`** on these routes and on
`/api/direct-upload/*` and `/api/articles/:id/assets/:assetType`. The two ImgBB
upload routes use `image` instead, and `/api/direct-upload/*` additionally
requires an `articleId` form field.

### Uploaded files

Images: JPEG, PNG, GIF, WebP, HEIC/HEIF, AVIF, 10 MB by default. HEIC and AVIF
are transcoded to JPEG. **SVG is rejected** — it is scriptable and these files
are served back to readers.

Archives: ZIP containing HTML plus its images. 50 MB by default, expanding to at
most 200 MB across at most 500 entries and 60 images. Bundled images are
re-hosted and the HTML rewritten to point at them.

**All HTML is sanitized before storage.** Scripts, iframes, event handlers and
`javascript:` URLs are removed. The response reports `sanitized: true` when
anything was stripped — on the contributor and article-asset routes;
`/api/direct-upload/html-zip` returns only `{success, message}`.

Every upload's real format is verified from its leading bytes, not its declared
content type or extension.

## Re-upload sessions

Replacing the content of a live article without serving a half-updated version.

```
POST /api/articles/:id/reupload           (auth)  open a session
POST /api/articles/:id/reupload/complete  (auth)  republish
POST /api/articles/:id/reupload/cancel    (auth)  restore the previous status
POST /api/public-upload/:token/complete   (token) contributor finishes their own session
```

Opening returns `201 { article, uploadUrl, expiresAt }` — note `uploadUrl`, and
no token field; the secret is inside the URL. It drops the article to draft, sets
`isReuploading`, tells the live site to remove it, revokes any older links for
that article and issues one new link covering every asset type. Both publishers
skip the article while the session is open.

Preconditions worth knowing:

| Call | Fails with |
|---|---|
| open, when one is already open | 409 |
| open, on an article that is neither published nor finished | 400 |
| complete or cancel, with no session open | 409 |
| complete, when the article has no content | 400 |

Nothing is published until completion, which republishes, keeps the article's
original publication date, syncs Airtable and refreshes the site cache.

## Integration settings

`/api/integration-settings/*` is admin-only and holds the Airtable, ImgBB and
GitHub credential rows.

Values whose key looks like a credential — matching `key`, `token`, `secret`,
`password` or `credential` — come back masked as `••••1234` with
`configured: true` and `redacted: true`. **Other keys are returned verbatim**,
with only a `configured` flag. Table names and toggles are not secrets and are
not masked.

The service-specific reads `GET /api/airtable/settings` and
`GET /api/imgbb/settings` are `auth` rather than `admin`; their values are
redacted by the same rule. Writing credentials is admin on every route.

## Webhooks

`POST /api/webhooks/article-published` triggers a full Airtable article sync.

It requires `x-webhook-secret` when `WEBHOOK_SECRET` is set, compared in constant
time. **If `WEBHOOK_SECRET` is unset the endpoint is open** — it only logs a
warning in production. Set it, or anyone can force repeated syncs and exhaust
your Airtable quota.

## Diagnostics

Five Airtable diagnostic routes write to **real Airtable records** to prove the
integration can write. They are admin-only, and they are mounted when
`ENABLE_DIAGNOSTIC_ROUTES=true` **or** whenever `NODE_ENV` is not `production` —
so they are on by default in development.

> Pointing a local server at your production Airtable base will mutate it.
